# CUDA MoE speed

Branch `x/cuda-moe-speed`, based on `4c7c24c10` (`feature/all-backends`, tree = published main `c8f55083c`).
- Candidate: commit `cf7d1f2d9`. Engine sha256 is in `receipts/build-shas.txt`.
- Gates: [PREREG.md](PREREG.md), frozen before any candidate measurement. Amendment 1 fixes the prefill
  instrument; it is post-hoc and says so.
- Receipts are in `receipts/`. The scripts that made them are in `scripts/`; the big-file scratch directory is
  written as `$BIG`.
- Every file is synthetic. No real MoE checkpoint was loaded.
- `tools/gguf2pack.c`, the sidecar and the `table.bin` format are **unchanged**: the sidecars are
  byte-identical, so this merges cleanly next to the Metal MoE lane.

## What changed

The numeric class is **bit-exact**. Every dot product keeps the earlier build's f32 operation order:
- lane l sums groups l, l + 32, ... in turn, then the xor butterfly;
- the router softmax trees are unchanged;
- top-k gives the same ids and weights, in the same ranks;
- the down sum runs in rank order.

The outputs are identical to the base build on every gate file (G-BITS below).

`tools/payload-moeany.patch`, generated by `scripts/edit_speed.py`:
- **`llb_moe_gu` / `llb_moe_dn` bodies:** each kernel works in 256-column units. A lane's two groups of a unit
  are loaded before any decode. Each unit's f16 scales and 6-bit scale/min codes are decoded once a unit, not
  once a group, and the 4-bit and 6-bit integers become floats through the exact 2^23 magic instead of I2F. The
  values are the same as q4k_w / q5k_w / q6k_w / q8g_w; only fewer instructions make them. Gate and up of a row
  run in one pass.
- **`llb_moe_dn`:** four experts a round. The shared expert's down GEMV is folded in where `llb_kgemv` would have
  run `llb_gemv_any`, which has the same leaf and order. The kernel is held to 64 registers
  (`__launch_bounds__(128, 8)`).
- **`llb_moe_topk`:** for up to 1024 experts, warp 0 does the selection. Each lane keeps its best expert, and a
  round is `__reduce_max_sync` on the probability bits, then `__reduce_min_sync` on the index. The order (p
  descending, then index ascending) is the old block argmax's. The shared expert's silu runs in the same launch
  (blocks 1..).
- The 1024-thread max / exp / sum part is unchanged, so its float trees are too.

`host/llb_host.c`:
- **Fused launches:**
  - the router and the shared-expert gate are one F32 GEMV launch when their rows are adjacent (gguf2pack's name
    order puts them next to each other);
  - the shared gate and up are likewise one launch;
  - the F32 GEMVs take a warp a row instead of the default grid's idle warps.
  - Launches per MoE layer go from 10 to 6.
- **CUDA graph:** a MoE file records each folded step as a CUDA graph (`LLB_GRAPH`'s existing replay) unless
  `LLB_GRAPH` is set. Dense files are untouched.
- **Stream residency:**
  - the chosen experts are copied from the mmapped GGUF into pinned host slots by 8 threads;
  - each slot goes to the device with `cuMemcpyHtoDAsync` while the next slot is filled;
  - the expert kernels queue behind the copies. Before, there were 24 synchronous pageable copies per layer.
- **`LLB_STEP_US=1`:** prints the whole token period (`stepus POS US`), env only. The base arm for speed is
  `4c7c24c10` plus this hunk only (`scripts/timer-only.patch`).

Things that were tried and not kept (dev nsys, S35 Q4_K_M, us per launch; `scripts/tryvar.sh`):

| change | result | kept? |
|---|---|---|
| gu: 2 rows a warp | 28.8–32 vs 25.7 | no |

## Profile: where the token goes (nsys, S35 Q4_K_M, steady-state step; `receipts/prof/final-*.txt`)

Under nsys the period is 1.85 ms (base) and 1.51 ms (candidate). Without nsys it is 1.70 ms and 1.24 ms. The
period has two parts:
- **outside the pass:** the Bend program, unified-memory traffic and host gaps;
- **inside the pass:** from the embed kernel to delivery.

| per token | base | candidate |
|---|---|---|
| outside the pass | 821 us | 880 us |
| pass span | 1030 us | 632 us |
| `bend_dev` (16 launches) | 330 us | 330 us |
| launches | 131 | 113 |

The outside-the-pass part is the same on the dense 0.8B (919 us, `receipts/prof/base-08b.txt`): it is the
engine's per-token loop, not the MoE path.

MoE FFN per layer, GPU us per launch:

| piece | base | candidate |
|---|---|---|
| `llb_moe_gu` (8 experts gate + up + silu) | 58.4 | 24.9 |
| `llb_moe_dn` (down, weighted sum, residual) | 32.5 | 17.7, with the shared down folded in |
| `llb_moe_topk` | 18.4 | 9.3, with the shared silu folded in |
| router + shared gate (F32) | 8.4 + 7.4 | 6.0 (one launch) |
| shared gate, up, silu, down | 5.4 + 5.0 + 3.1 + 5.2 | 5.6 (one launch; silu and down folded) |
| total, about | 150 | 68 |

The trunk of each layer (attention or delta-net plus norms, about 70 us) is the dense engine's code, unchanged.

## Speed

Method (prereg):
- The engine figure is the median `LLB_STEP_US` period over decode positions ≥ 12 (P1, 128 steps). The prefill
  figure is a 512-id prompt, summed over positions 3–511 (amendment 1).
- llama.cpp is `llama-bench` build 9d57ce45, tg128 `-r 5` and pp512 `-r 3`.
- There are 3 interleaved rounds per arm; the figures are medians.
- The 4-layer files were read from `/dev/shm`, because the stream residency needs a page-cacheable file. On the
  ntfs-3g FUSE disk an mmapped stream gets about 1 tok/s.
- Rounds are in `receipts/speed/r1..r3`; the summary is `receipts/speed/SPEED.txt`.

### Targets (frozen)

| target | result | verdict |
|---|---|---|
| T1: device ≥ 0.8x llama.cpp on S35 | 0.46x | **MISS** |
| T2: marginal per layer ≤ 1.25x llama.cpp | 1.26x (154 vs 122 us; rounds 1.08 / 1.29 / 1.26) | **MISS by 0.007** |
| T3: host ≥ 1.2x base | 1.08x | **MISS** |
| T3: stream ≥ 1.5x base | 1.61x | PASS |
| T4: no regression (device / host / stream, both files) | all faster (1.05x to 1.76x) | PASS |

Why the misses happened:
- **T1:** the per-token loop outside the layers (`bend_dev`, unified-memory page traffic, host gaps) is about
  0.8 ms of the 1.24 ms token. The dense 0.8B has the same cost. llama.cpp's whole token is 0.56 ms. A 4-layer
  file is dominated by that fixed part. The prereg predicted this miss before any candidate run. Removing it
  means changing the Bend runtime's token loop, which is not MoE work and was not touched here.
  - On a 40-layer 35B-A3B the same per-layer costs project to about 0.8 + 40 x 0.154 = 7.0 ms against
    llama.cpp's 0.07 + 40 x 0.122 = 4.95 ms, roughly 0.7x. That is a projection from synthetic layers, not a
    measurement.
- **T2:** the per-layer gap is about 32 us. About half is the trunk, which is dense code and unchanged. The rest is
  the exact f32 expert dot products against llama.cpp's int8 dp4a:
  - gate + up: 24.9 us here, about 18 us there;
  - down: 17.7 us here, about 10 us there.

  Round-to-round spread (1.08 to 1.29) is wider than the miss; another llama-server was resident on the GPU
  throughout.
- **T3 host:** the host residency reads about 60 MB of chosen experts per token over PCIe. At 23 GB/s it is
  already at the bus rate, so better kernels cannot buy more.
  - llama.cpp's `-ot exps=CPU` avoids the bus and runs the experts on 16 CPU threads instead. It gets 2.1x more.

Not done (next steps, each its own prereg):
- **A dp4a MoE tier.** It changes numerics: int8 activations with a declared tolerance, judged by G-X. That is
  where most of the T2 gap is.
- **Batched MoE prefill:** route the prompt's tokens per expert as a mat-mat.
- **A CPU-expert option for the host residency.**
- **Speculative next-layer prefetch for stream.** With random synthetic routing it can only waste bandwidth, so
  it was not built.

## SUMMARY

- **Built (bit-exact):**
  - faster routed-expert kernels: unit bodies with loads first, scales decoded once a unit, the exact 2^23
    integer path;
  - 4 experts a round in the down kernel, with the shared down folded in;
  - warp-level top-k with the shared silu folded in;
  - adjacent GEMVs fused, so MoE launches per layer go from 10 to 6;
  - each MoE step run as a CUDA graph;
  - a pinned, threaded, async stream residency.
  - gguf2pack, the sidecar and the table format are unchanged.
- **Correctness PASS:**
  - G-BITS 48/48 identical to the base on 8 files;
  - G-X 192/192 on the 7 files that have an F32 reference, rms ≤ 0.0027;
  - G-MODE 24/24;
  - G-REG 28/28;
  - G-SIDE 12/12;
  - the subtle mutant (3e-6 rms) and the garbage mutant both FAIL, as they must.
- **Speed, decode tok/s:**

  | file | arm | before | after | llama.cpp CUDA |
  |---|---|---|---|---|
  | S35 Q4_K_M | device | 589 | 807 | 1772 (0.46x) |

  | S128F Q4_K_M | device | 718 | 917 | 2196 (0.42x) |

  - The MoE FFN per layer went from about 150 to 68 us of GPU time.
  - Each added MoE layer costs 154 us (before: 222), against llama.cpp's 122 us: 1.26x.
- **Targets:**
  - T1 (0.8x end to end) **missed**: the engine's fixed per-token loop of about 0.8 ms is not MoE code.
  - T2 (per-layer ≤ 1.25x) **missed by 0.007** at 1.26x.
  - T3 host (1.2x) **missed** at 1.08x: the bus is the limit.
  - T3 stream (1.5x) **passed** at 1.61x.
  - T4 no regression **passed**.
- **Prefill:** still one token at a time (755 tok/s against llama.cpp's 26,596). Batched MoE prefill and a dp4a
  tier are the next steps.
